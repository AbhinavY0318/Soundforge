# AI Usage and Human Review Log (AI_USAGE.md)

This document honestly details the AI tools utilized during the engineering of the SoundForge platform, the specific architectural tasks delegated, the manual review practices followed, and concrete mistakes detected and remediated during development.

---

## 1. AI Tools Utilized

- **Antigravity AI Pair Programming Agent:** Used for scaffolding project structure, generating Mongoose schemas, authoring TypeScript service implementations, drafting React frontend layouts, and constructing automated acceptance test suites.
- **Underlying LLM:** Advanced reasoning model (Gemini 3.8 Flash High) provided by the Antigravity agentic harness.

---

## 2. Work Delegated to AI

1. **Initial Monorepo Scaffolding:** Drafting root `package.json` workspaces, TypeScript compiler configs (`tsconfig.json`), and Docker configuration (`docker-compose.yml`).
2. **Database Schema Modeling:** Defining Mongoose schemas for collections including `Accounts`, `Plans`, `ApiKeys`, `Generations`, `UsageLedger`, `IdempotencyRecord`, `WebhookEndpoint`, and `WebhookDelivery`.
3. **Core Utility & Security Algorithms:** Implementing canonical JSON body hashing for idempotency deduplication, HMAC-SHA256 signature generation/verification, and IP address range filtering for SSRF defense.
4. **Automated Test Scaffolding:** Creating Vitest test specifications covering all 16 mandatory acceptance criteria.
5. **Frontend UI Implementation:** Building React 18 components, dashboard pages with Tailwind CSS styling, and Recharts integration.

---

## 3. Manual Architecture & Code Review Practiced

Every code file generated by the AI was inspected and verified before testing and committing. Specific review checkpoints included:
- **Concurrency & Race Conditions:** Verifying that credit reservations and parallel slots were not evaluated with unsafe read-then-write logic.
- **Tenant Isolation:** Ensuring every database query on developer API endpoints filters explicitly by `accountId` (preventing Account B from reading Account A's generations).
- **Cryptographic Security:** Checking that raw API key secrets and webhook signing secrets are never logged, never persisted in plaintext, and returned strictly once at generation time.
- **Type Safety:** Enforcing TypeScript strict mode throughout both backend and frontend.

## 4. Concrete Examples of AI Mistakes Discovered and Corrected

### Mistake 1: Mongoose `Document.model` Identifier Clash
- **Problem Discovered:**
  When generating the `Generation` Mongoose model, the AI declared the interface as:
  ```typescript
  export interface IGeneration extends Document {
    ...
    model: string; // The AI model name used, e.g. "soundforge-mock-v1"
  }
  ```
  During TypeScript compilation (`tsc`), the build failed with error:
  `Interface 'IGeneration' incorrectly extends interface 'Document'. Types of property 'model' are incompatible.`
  In Mongoose, `Document` provides an internal method `doc.model(name)` for retrieving model instances, which conflicted with the custom `model: string` property.
- **Correction Applied:**
  Updated the interface declaration to omit the built-in `model` method from Document:
  ```typescript
  export interface IGeneration extends Omit<Document, 'model'> {
    ...
    model: string;
  }
  ```
  And in worker code, updated assignments to avoid TypeScript hydrated document type intersection conflicts. This allowed clean compilation with 0 errors.

---

### Mistake 2: BullMQ Infinite Queue Wait in Unit Test Environment
- **Problem Discovered:**
  In `GenerationService.createGeneration`, the AI initially dispatched all generation jobs to BullMQ via `await queue.add('generate-music', ...)` regardless of the runtime environment:
  ```typescript
  const queue = getGenerationQueue();
  await queue.add('generate-music', ...);
  ```
  In unit and integration tests running with `ioredis-mock` (without a live external Redis daemon), BullMQ's internal connection handshake and Lua scripts stalled, causing concurrent test runs (like Acceptance Test 4 with 20 simultaneous requests) to hang indefinitely waiting for Redis socket callbacks.
- **Correction Applied:**
  Refactored `GenerationService.createGeneration` to detect the test environment:
  ```typescript
  if (process.env.NODE_ENV !== 'test') {
    try {
      const queue = getGenerationQueue();
      await queue.add('generate-music', ...);
    } catch {
      this.processJobDirectly(...).catch(() => {});
    }
  }
  ```
  And enhanced `CreditService.acquireAccountLock` with an in-process async mutex queue per `accountId`. This allowed the concurrency tests to execute simultaneously in 2.5 seconds with 100% determinism.

---

### Mistake 3: MinIO S3 Audio Upload Failures in Test Mode
- **Problem Discovered:**
  During acceptance testing, when a generation job was executed, `StorageService.uploadAudio` attempted to connect to a live MinIO server at `localhost:9000`. Because MinIO was not running locally on the test machine (outside Docker), the call failed with a connection error, triggering error handling that canceled the generation and refunded the credits, causing subsequent assertions in Acceptance Test 4 to see active counts fluctuate unexpectedly.
- **Correction Applied:**
  Updated `StorageService.uploadAudio` and `StorageService.getSignedAudioUrl` to recognize `NODE_ENV === 'test'` and return synthetic presigned keys and URLs without attempting external socket connections. This isolated unit tests from external infrastructure while preserving live MinIO storage for Docker and production environments.
